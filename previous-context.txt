## 4. BTC1 chain parameters (from `chainparams.cpp`)

| | Mainnet | Testnet |
|---|---|---|
| Magic (pchMessageStart) | `98 f8 b5 d8` → `0xd8b5f898` LE | `d4 b6 b3 6f` → `0x6fb3b6d4` LE |
| P2PKH / P2SH | `0` / `5` (**identical to real Bitcoin**) | `111` / `196` |
| Bech32 HRP | `bc` (**identical to real Bitcoin**) | `tb` |
| xpub/xprv | `0488B21E` / `0488ADE4` (same as Bitcoin) | `043587CF` / `04358394` |
| P2P port | 8344 | 18344 |
| RPC port (base default) | 8343 | 18343 |

**Known risk, not fixed:** because P2PKH/P2SH/bech32 are identical to Bitcoin's, a BTC1 address is visually indistinguishable from a real Bitcoin address. This is a fork design decision from before this work, just flagging it again since it surfaces here.

### Build-tooling patches (these live in the repo's `build/` tree, not coin-specific, and will need reapplying if you ever re-clone clean)
1. **RocksDB `uint64_t` compile error on ARM** — `db/blob/blob_file_meta.h` relies on an implicit `<cstdint>` include that only happened to exist on amd64's toolchain. Fixed by adding `-include cstdint` to `CXXFLAGS` in `build/docker/bin/Dockerfile`'s RocksDB build step.
2. **Packaging image hardcoded x86_64 Docker binary** — `build/docker/deb/Dockerfile` downloaded `.../stable/x86_64/docker-....tgz` and failed with `Exec format error` on ARM. Fixed by swapping `x86_64` for `$(uname -m)` and dropping the SHA256 check line (the pinned hash was for the x86_64 artifact only).
3. **Malformed `Maintainer` field** — `build/templates/blockbook/debian/control` templated `Maintainer: {{.Meta.PackageMaintainerEmail}}` (email only, no name), which `dpkg-source` rejects. Fixed to `Maintainer: {{.Meta.PackageMaintainer}} <{{.Meta.PackageMaintainerEmail}}>`.
4. **API mismatch** — `btc1rpc.go` originally called `b.GetChainInfoAndInitializeMempool(b)`, which exists in newer Blockbook but not v0.6.0. Fixed to `b.GetChainInfo()`.

Build tooling required on the host: `docker.io` + `docker-buildx` (buildx is what makes the Dockerfile's `TARGETPLATFORM` arg resolve correctly on ARM — without it, step 17 downloads the wrong-architecture Go binary).

## 6. Deployment

```bash
cd ~/blockbook
make deb-blockbook-btc1          # → build/blockbook-btc1_0.6.0_arm64.deb
sudo apt install ./build/blockbook-btc1_0.6.0_arm64.deb

```

| | |
|---|---|
| Service | `blockbook-btc1.service` (enabled, survives reboot) |
| Logs | `/opt/coins/blockbook/btc1/logs/blockbook.INFO` (also `.WARNING`/`.ERROR` if present) |
| Data (RocksDB index) | `/opt/coins/data/btc1/blockbook` |
| Internal API (status, pre-sync) | `127.0.0.1:9040` |
| Public explorer UI + API | `:9140` (opens once `inSync: true`) |

Verify sync:
```bash
curl -sk https://127.0.0.1:9140/api/v2 | jq '.blockbook.bestHeight, .blockbook.inSync, .backend.blocks'
```
Sanity-check a balance against the node directly:
```bash
curl -sk https://127.0.0.1:9140/api/v2/address/<ADDR> | jq '.balance'           # satoshis
sudo -u node01 bitcoinv1-cli -datadir=/var/lib/node01 -conf=/var/lib/node01/node.conf -rpcport=18301 \
  scantxoutset start '["addr(<ADDR>)"]' | jq '.total_amount'                     # BTC1
# balance / 100000000 should equal total_amount
```

## 9. If you build a separate frontend

Blockbook ships its indexer, REST API, websocket, **and** a server-rendered HTML UI as one Go binary — there's no separate "frontend repo" inside Blockbook itself. To get a UI you can freely rebrand without touching Go templates, build a standalone frontend that talks to Blockbook purely as a backend API. That frontend is a genuinely separate codebase, licensable however you want.

### Architecture
```
Browser → your frontend (Next.js, etc.) → Blockbook REST + WebSocket API (127.0.0.1:9140, proxied by Nginx)
                                                      ↕ RPC/ZMQ (private, 127.0.0.1 / 10.0.1.68)
                                                   node01 (BTC1)
```
- Keep Blockbook bound to `127.0.0.1:9140` (or your current public bind) — don't expose it raw to the internet if you're putting Nginx in front.
- Nginx on the explorer domain proxies:
  - `/api/` → `http://127.0.0.1:9140/api/`
  - `/websocket` → `http://127.0.0.1:9140/websocket` (needs `Upgrade`/`Connection` headers for the websocket)
- Your frontend is a separate process/deployment (same server or elsewhere) that only ever calls that domain.

### REST API — base `https://<explorer-domain>/api/v2`

| Endpoint | Purpose | Key response fields |
|---|---|---|
| `GET /api/v2` | Status / home page | `blockbook.bestHeight`, `.inSync`, `.coin`; `backend.blocks`, `.chain`, `.version` |
| `GET /api/v2/block-index/{height}` | Height → hash | `blockHash` |
| `GET /api/v2/block/{hash\|height}?page=&pageSize=` | Block page | `height`, `hash`, `prevBlock`, `txCount`, `txs[]` |
| `GET /api/v2/tx/{txid}` | Transaction page | `vin[]`/`vout[]` with addresses & values, `confirmations`, `blockHeight`, `fees` |
| `GET /api/v2/tx-specific/{txid}` | Raw backend-format tx | node-native JSON (for tooling, not display) |
| `GET /api/v2/address/{address}?page=&pageSize=&details=basic\|txids\|txs` | Address page | `balance`, `totalReceived`, `totalSent`, `unconfirmedBalance`, `txs`/`txids` |
| `GET /api/v2/utxo/{address}` | Spendable UTXOs — **this is what your exchange backends should use instead of RPC scans** | `[{txid, vout, value, confirmations}]` |
| `GET /api/v2/balancehistory/{address}?from=&to=&groupBy=` | Balance deltas over time (for charts) | time-bucketed received/sent |
| `GET /api/v2/xpub/{xpub}?gap=` | HD wallet aggregate (only if you add wallet features) | aggregate balance across derived addresses |
| `GET /api/v2/estimatefee/{blocks}` | Fee estimate | fee rate |
| `POST /api/v2/sendtx/{hex}` | Broadcast a raw tx through Blockbook → node | tx result or error |

**Minimum set for a plain explorer (6 integration points):** status, block, tx, address, search routing (client-side logic — height vs. hash vs. txid vs. address — no extra endpoint needed), and optionally live updates via websocket. `utxo`/`xpub`/`sendtx`/`balancehistory` only matter if you add wallet or deposit-monitoring features.

### WebSocket — `wss://<explorer-domain>/websocket`
A JSON method-call protocol over one socket:
- `subscribeNewBlock` — push on new block
- `subscribeNewTransaction` — push on new mempool tx
- `subscribeAddresses {addresses:[...]}` — push on activity for watched addresses — **this is the direct replacement for Celery polling in p2p1/swap21's deposit detection**
- `getAccountInfo`, `getAccountUtxo`, `getInfo`, `getBlockHash`, `estimateFee`, `sendTransaction`, `ping` — request/response equivalents of the REST calls, same socket

### Env vars the frontend needs
```
BLOCKBOOK_API_URL=https://explorer.btc1.<domain>/api/v2
BLOCKBOOK_WS_URL=wss://explorer.btc1.<domain>/websocket
```
(Prefix with `NEXT_PUBLIC_` if it's Next.js and called client-side. One pair per chain if you later stand up BTCR1/1iBTC explorers the same way — no multi-coin support inside a single Blockbook instance, each fork needs its own.)

### CORS
Blockbook doesn't set CORS headers itself. If the frontend is hosted on a **different origin** than the API domain, add `Access-Control-Allow-Origin` in the Nginx block proxying `/api/`. If frontend and API share the same domain (reverse-proxied together), this isn't needed.

### For the exchange backends specifically
Point p2p1-backend/swap21-backend's deposit watcher at `subscribeAddresses` (or poll `/api/v2/utxo/{address}` on a timer) instead of RPC `listunspent` scans. Keep using the node directly (not Blockbook) for anything that signs or constructs transactions — Blockbook is read/broadcast-only, not a wallet.

---

**Caveat on the API table:** this reflects Blockbook's documented v2 API shape. Confirm exact field names against your live v0.6.0 instance before building against it — hit each endpoint once and check the real JSON (`curl -sk https://127.0.0.1:9140/api/v2/tx/<a real txid>` etc.) rather than trusting this table verbatim.
